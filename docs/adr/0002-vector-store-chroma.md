# ADR-0002: 벡터 스토어 Chroma(로컬 persist)와 검색 전략

- 상태: 채택
- 날짜: 2026-09-02

## 상황

RAG 코퍼스는 `data/raw/` 아래 마크다운 5개다 — 주택임대차보호법 핵심 조문, 소액임차인 최우선변제 기준표, 전세사기 예방 체크리스트, HUG 전세보증금반환보증, 주택도시기금 전세자금대출. 청킹 후 규모는 **53청크**. 문서마다 `title / source / effective_date / category` frontmatter를 갖고, 답변에 출처 URL과 시행일을 붙여야 한다.

즉 필요한 것은 대규모 분산 검색이 아니라 **수십~수백 청크에 대한 메타데이터 포함 top-k 검색**이고, 데모(Streamlit)에서 서버 기동 없이 바로 떠야 한다.

## 결정

**Chroma를 로컬 `persist_directory`(`data/chroma/`)로 사용한다.**

검색 전략도 이 ADR에 함께 기록한다. 아래 다섯 가지는 모두 2026-09-02 실측을 거쳐 결정되었고, 일부는 **초기 선택을 실측이 뒤집은 결과**다.

| 항목 | 값 | 구현 위치 |
|---|---|---|
| 분할 | `MarkdownHeaderTextSplitter`(`#`,`##`) 우선, 초과 섹션만 문자 분할 | [`rag/ingest.py`](../../src/rent_agent/rag/ingest.py) `split_documents` |
| `chunk_size` | **1000** (`DEFAULT_CHUNK_SIZE`), overlap 100 | 같음 |
| 제외 섹션 | `## 출처` (`EXCLUDED_SECTION_PREFIXES`) | 같음 |
| 검색 타입 | `similarity` (MMR 아님) | [`rag/retriever.py`](../../src/rent_agent/rag/retriever.py) |
| `k` | **6** (`Settings.retriever_k`) | [`config.py`](../../src/rent_agent/config.py) |
| 문서 ID | `f"{file}#{순번}"` 결정적 업서트 | `rag/ingest.py` `chunk_ids` |

## 근거

### 스토어 선택

- **규모 적합**: 53청크. 인덱스 튜닝이나 샤딩이 문제가 되는 규모가 아니다.
- **메타데이터**: Chroma는 청크 메타데이터를 1급으로 저장·필터한다. `source`/`effective_date`를 답변 인용에 그대로 쓰므로 필수 요구사항이다.
- **서버 불필요**: `persist_directory`만 있으면 프로세스 내에서 동작한다. `uv sync` → `scripts/ingest.py` → `streamlit run` 세 줄로 재현되는 것이 포트폴리오 관점에서 중요하다.
- **langchain 통합**: `langchain-chroma`가 퍼스트파티로 유지된다.

### 검색 전략 — 실측으로 바뀐 결정들

**① 헤더 우선 분할 (초기: 문자 분할만)**

`RecursiveCharacterTextSplitter`만 쓰면 `## ` 경계에서 자른 뒤 `chunk_size` 미만 조각을 **다시 병합**해 "문서 서문 + 첫 조문"이 한 청크가 된다. 실제 저장소에서 "전입신고 대항력" 질의의 임베딩 거리를 재보니:

| 청크 | 거리(작을수록 가까움) |
|---|---|
| 서문 + 첫 조문 병합 청크 | **1.23** |
| 대항력 조문 단독 | **1.05** |

병합 때문에 정답 조문이 1위를 놓쳤다. → `MarkdownHeaderTextSplitter`로 섹션을 먼저 나누고, `chunk_size`를 넘는 섹션만 문자 기준으로 추가 분할한다. 조문 하나가 대개 300~800자라 **섹션 = 청크**가 성립한다.

**② `## 출처` 섹션 제외**

URL 목록이 코퍼스의 약 10%를 차지하면서 top-4에 끼어들었다. 출처는 이미 메타데이터 `source`로 제공되므로 검색 대상에서 뺀다. 청크 본문 앞에는 `[문서 제목] `을 붙여, 맥락이 약한 섹션 청크도 어느 문서인지 알 수 있게 했다.

**③ MMR → 단순 유사도 (초기 선택을 뒤집음)**

초기 구현은 MMR 리트리버였다(커밋 `62225c1` "…Chroma 인제스트 및 MMR 리트리버"). 교체는 코드 커밋 `3ab9053` "feat(rag): 헤더 우선 분할, 출처 섹션 제외, 유사도 검색, 결정적 id 업서트"에서 이루어졌고, 근거 문서화는 `5fdd12e` "docs: … MMR→유사도 …"에 있다. 그런데 이 코퍼스는 **섹션당 1청크인 비중복 구조**여서 MMR의 다양성 항이 억제할 중복이 없다. 결과적으로 다양성 항은 무관한 문서를 끌어올렸다.

| 검증 질의 수 | 관련 청크가 밀려난 질의 수 |
|---|---|
| 4 | **3** |

→ `search_type="similarity"`로 교체. (질의별 상세 표는 기록에 남지 않았다 — **미확인**. 남은 것은 위 집계값이다.) RAGAS 평가에서 중복이 문제로 드러나면 그때 재검토한다.

**④ 결정적 ID 업서트**

`Chroma.from_documents(..., ids=[f"{file}#{i}"])`. 같은 문서를 다시 적재하면 같은 ID가 나오므로 Chroma upsert가 갱신으로 처리한다. `scripts/ingest.py --no-reset`이 실제로 "기존 유지 후 갱신"이 되도록 하기 위한 조건이다. `reset` 경로에서는 디렉터리를 `rmtree`하지 않고 `reset_collection()`으로 컬렉션만 비운다 — 같은 경로를 이미 연 chromadb 클라이언트가 있으면 rmtree 후 쓰기에서 `attempt to write a readonly database`(SQLite code 1032)가 발생하기 때문이다.

**⑤ `k` 4 → 6 (RAGAS Q9 실측)**

RAGAS **3차** 평가 결과를 두고 Q9("청년전용 버팀목 전세자금대출의 연령 요건")를 추적한 결과, 정답 섹션 `## ② 청년전용 버팀목`이 유사도 **6~7위**로 밀려 top-4에 들어오지 못했다. top-4는 비교표(1위)·중기청(2위)·공통 요건(3위)·일반 버팀목(4위)으로 채워졌다. 상품 비교형 질의는 관련 섹션이 구조적으로 4~6개다. → `retriever_k` 기본값을 **4에서 6으로** 올렸고, 이 변경이 반영된 첫 측정이 **4차**다(아래 표).

**⑥ `chunk_size` 800 → 1000 (RAGAS Q9, 같은 추적의 마지막 단계)**

k=6으로 올린 뒤에도 Q9의 faithfulness는 0.57에 머물렀다. 원인은 분할이었다 — 섹션 ②가 800자 기준으로 **734자 본문**(연령표·병역 예외)과 **210자 꼬리**(실무 팁)로 갈리고, 꼬리에 "만 34세 이하라면 청년전용" 문장이 있어 **꼬리가 본문보다 먼저** 검색됐다(6위). 답은 문서와 일치했지만 근거 청크가 컨텍스트에 없어 faithfulness가 정당하게 감점된 것이다.

실측한 가장 긴 섹션은 **816자**(`05-youth-jeonse-loan.md`의 `## ② 청년전용 버팀목 전세자금 — 연령·소득·한도 요건`)이므로, `chunk_size`를 **1000**으로 올리면 모든 `##` 섹션이 한 청크가 되고 여유(약 180자)까지 남는다. (참고: `src/rent_agent/rag/ingest.py:26` 주석은 이 값을 "≈950자"로 적어 두었다 — 코드 동작에는 영향이 없는 주석상의 과대 기재다.) 회귀 방지로 `tests/rag/test_ingest.py::test_real_corpus_chunking_is_stable`에 "(file, section) 조합 중복 없음" 단언을 추가했다.

### 지표 변화 (2026-09-02 ~ 09-03, 각 회차 n=10)

| 회차 | 변경 | faithfulness | answer_relevancy | context_precision |
|---|---|---|---|---|
| 1차 | 기준선 (k=4, chunk 800) | 0.881 | 0.382 | 0.900 |
| 2차 | Q4 검색 어휘 보강 + 프롬프트(대체 답 금지) | 0.822 | 0.414 | 0.950 |
| 3차 | 프롬프트(상품 간 조건 혼용 금지) | 0.902 | 0.392 | 0.950 |
| 4차 | 데이터셋 reference 수정 + 섹션 헤더 보강 + **k 4→6** | 0.911 | 0.436 | 0.832 |
| 5차 | **chunk_size 800→1000** (53청크) | 0.914 | 0.391 | 0.886 |
| **6차(최종)**<br>2026-09-03 00:06 | **faithfulness 컨텍스트를 에이전트가 실제 본 `ToolMessage`로 변경** (k=6, 53청크) | **0.961** | 0.425 | 0.851 |

해석 규칙:
- `context_precision`은 **k 변경 전후를 비교하지 않는다**. 4차의 0.832는 k=6 첫 측정값이며, 5차의 0.886은 같은 k=6인 4차 대비 상승(조각 청크가 온전한 섹션으로 대체된 효과)이다.
- `answer_relevancy`는 절대 임계값(영어 벤치마크 0.8)과 비교하지 않는다. 한국어 + `text-embedding-3-small`에서 정답도 0.2~0.7에 머물고 정직한 "자료에 없음" 답은 0점 처리되므로, **실행 간 기준선**으로만 쓴다.
- n=10이므로 **±0.05는 판정 변동 범위**다. 2차의 faithfulness 하락(0.881→0.822) 대부분은 검색이 불변인데 P가 움직인 Q1이 보여주듯 판정자 엄격도 차이였다.
- **`faithfulness`는 6차 이후만 비교 가능하다.** 1~5차는 평가 스크립트가 따로 돌린 검색 결과를 컨텍스트로 썼는데, 10문항 중 **6문항에서 에이전트의 실제 검색 질의가 원 질문과 달랐다** — 즉 이전 방식은 에이전트가 보지 않은 문서를 근거로 환각을 판정했다. 6차부터는 에이전트가 실제 본 `ToolMessage`를 컨텍스트로 쓴다([`eval/results/2026-09-03.md`](../../eval/results/2026-09-03.md), 이력: [`eval/results/history.md`](../../eval/results/history.md)).
- 신뢰할 지표는 `faithfulness`(환각)와 `context_precision`(검색)이다.

## 검토한 대안

| 대안 | 장점 | 배제 이유 |
|---|---|---|
| **FAISS** | 빠르고 가볍다, 의존성 적음 | 메타데이터 저장·필터가 약해 별도 사이드카 저장소가 필요하다. `source`/`effective_date`를 답변에 인용하는 요구사항과 맞지 않는다. |
| **pgvector (PostgreSQL)** | 운영형, SQL 필터·트랜잭션, 확장성 | Docker/DB 기동이 실행 전제가 된다. 53청크 규모에 대해 얻는 것이 없고, "세 줄로 재현되는 데모"를 잃는다. |
| **인메모리 벡터 스토어** | 가장 단순 | 매 실행마다 재임베딩 → 시간·비용 낭비. `--no-reset` 증분 적재 시나리오가 불가능하다. |

## 결과/트레이드오프

- **얻은 것**: 서버 없는 재현 가능한 데모, 메타데이터 기반 출처 인용, 실측으로 검증된 검색 파이프라인(F 0.914 / P 0.886).
- **잃은 것**: 동시 쓰기·수평 확장은 없다. Chroma는 SQLite 기반이라 프로세스가 동시에 같은 디렉터리에 쓰면 락 문제가 난다(위 ④의 code 1032가 그 사례다).
- **교체 경로**: 벡터 스토어 의존은 `rag/ingest.py`(적재)와 `rag/retriever.py`(조회) 두 파일에 갇혀 있다. 에이전트는 `get_retriever(settings)`가 돌려주는 `VectorStoreRetriever`만 알기 때문에, pgvector로 옮길 때 이 두 파일만 바꾸면 된다.
- **`k=6`의 대가**: 컨텍스트 토큰이 k=4 대비 50% 늘어난다. 상품 비교형 질의의 정답 누락을 막는 값이므로 지불한다.
